A sitemap lastmod that tells the truth: hand-kept dates and a fingerprint test

8 October 2026

On 1 September 2026 I found that my site's sitemap lastmod changed every time anyone looked at it. Two fetches a second apart returned two different dates on all seven URLs. Nothing errored, and every page looked fine in a browser. The feed was simply telling search engines that every page changed constantly, which is a good way to get the field ignored.

The assumption behind new Date()

The sitemap route set lastModified: new Date() on every entry. It is the pattern the Next.js documentation's own sitemap.ts example uses, and it reads as harmless. I had treated it as "when the site was built".

On my setup that was wrong twice over. The route renders on every request, so new Date() meant "when the crawler happened to ask". That is why the sitemap changes on every request. Even on a build-time sitemap it would mean "when anything was deployed". A commit that touched only internal docs had already restamped the Ludo page, whose content had not changed.

What Google does with a sitemap lastmod

Does Google use lastmod at all? Its sitemap documentation is plain about it. Google uses <lastmod> only "if it's consistently and verifiably" accurate, for example when it matches the page's own last change. The value should reflect the last significant update, such as the main content, structured data or links. The same page says Google ignores the changefreq and priority fields entirely, so my XML sitemap leaves both out.

So a lastmod that always says "now" is not neutral. It fails the verifiable test on every URL, and because lastmod accuracy is judged on consistency, the honest dates go down with the dishonest ones.

Dates that come from the content

The fix was to stop asking the clock. This is the whole trick to lastmod in a Next.js sitemap: read a date, never make one.

Each game in the catalogue now carries an updated field, a plain YYYY-MM-DD string kept by hand. The sitemap reads it for that game's page. The homepage takes the later of its own date and the freshest game it lists, because it prints every game's name and blurb. ISO dates sort as strings, which is the whole reason for that format.

Each guide page also prints who wrote it and when it last changed, and that date moves only when the content does. The sitemap and the page now say the same thing.

When should lastmod change? When the words a searcher can see change, and not otherwise. Hand-kept dates have one obvious failure: someone edits the copy and forgets the date. That is what the test is for.

A fingerprint that fails when the copy moves

The test takes a content hash of everything a search result can see for a game page, and compares it with a stored fingerprint:

/** The fields that actually reach a search result for /play/<slug>. */
function indexedContent(game: Game): string {
  return JSON.stringify([
    game.slug, game.name, game.blurb, game.players, game.time,
    game.minSeats, game.maxSeats, game.ready,
    rulesFor(game.slug).map((rule) => [rule.name, rule.desc]),
    guideFor(game.slug) ?? null,
  ]);
}

function fingerprint(game: Game): string {
  return createHash('sha256').update(indexedContent(game)).digest('hex').slice(0, 12);
}

it('does not change between two calls', () => {
  const first = sitemap().map((e) => String(e.lastModified));
  const second = sitemap().map((e) => String(e.lastModified));
  expect(second).toEqual(first);
});

Edit a game's rules or guide and the hash changes. The failure message gives the new fingerprint and says what to do: set that game's date to today, then paste the fingerprint in. Forgetting becomes a red test instead of a stale sitemap.

What is left out matters as much. Purely visual fields are excluded, because a change of look changes nothing a crawler reads. The written guide was left out at first too. It went in on 27 September 2026, after four guides changed and no date moved with them.

The second test is the regression test for the original bug, and it demands a deterministic sitemap. Any new Date() in the sitemap makes two calls disagree by a millisecond, and it fails.

The test that passed while checking nothing

One check compares the homepage date with the freshest game. It once looked the homepage up by its old path. When the path changed, the lookup returned undefined, and String(undefined) >= "2026-09-01" is true, because "u" sorts after "2". The test went on passing with nothing behind it. It now asserts that the entry exists before comparing anything.

What it costs

The test fires often. Between 2 September and 4 October 2026, 23 commits changed at least one fingerprint, one of them a merge. Nearly all were copy changes that would otherwise have left a date behind; the exception was the day the guide joined the hash.

It also cannot judge significance. Fixing one typo in a guide moves that page's date, although Google would not call it a significant update. I accept that. A date that is sometimes early is better than one that is always "now".

A check you can copy

Fetch your own sitemap twice, a few seconds apart, and compare the bytes. I did that for mine on 8 October 2026: the two copies were identical across 37 URLs, with lastmod values spread over several dates, not one. If yours differ between fetches, something in the route is reading the clock.

Where this stops

This is one small site, and I have no data on whether Google now trusts its dates. The fingerprint covers the game pages only. The other pages keep their dates in a separate file; a test keeps each one in step with the date the page prints, but no hash watches their copy. And hand-kept dates rely on a person reading the failure message. The sitemap and the pages it dates belong to Boardit, the browser game site I build, if you want to compare them yourself.
